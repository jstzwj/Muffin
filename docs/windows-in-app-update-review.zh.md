# Windows 应用内更新：代码审查记录

审查日期：2026-10-30。

本轮按要求仅走读代码并修正发现的问题，没有运行构建、测试、签名脚本或实际安装升级。下述内容是实现契约及静态审查结论，不代表已完成端到端验证。

## 范围与流程

Windows 安装版使用应用内下载和重启更新；Windows 便携版、Linux 和 macOS 保持原有发布页下载入口。

1. 从 CNB 静态更新清单发现新版本，失败时读取 GitHub 静态附件；按当前应用架构选择 Windows x64 或 ARM64 安装包与更新清单。详见 [CNB 发布镜像](cnb-release-mirror.zh.md)。
2. 使用内置 ECDSA P-256 公钥验证清单签名，再流式下载并验证安装包大小与 SHA-256。
3. 用户选择“重启并更新”，更新器检查其他进程，锁定安装包，逐个检查窗口中的未保存内容。取消保存时保持窗口打开。
4. 保存各窗口的标签页、选区、阅读位置和目录状态。安装程序确认已就绪后，编辑器以排他创建方式写入 `update.ready.decision`，批准安装并退出。
5. 安装程序同时要求明确批准和原进程退出，才开始 MSI 安装。取消与批准使用同一个决策文件仲裁；普通退出或崩溃不能代替批准。
6. MSI 在事务内移除旧产品；失败时由 Windows Installer 执行回滚。安装程序完成后以原用户权限重新启动应用。
7. 应用恢复窗口，并初始化文件打开分发器；后续从资源管理器打开文件仍走正常路径。

## 本轮修正

| 问题 | 处理 |
| --- | --- |
| 恢复更新会话的启动分支没有启用文件打开分发器 | 返回恢复的主窗口，并调用正常分发器初始化入口 |
| 保存对话框的嵌套事件循环允许重复触发重启、改变窗口集合 | 在首个保存提示前进入准备状态，阻止重复操作和未经批准的窗口关闭 |
| 更新期间收到打开文件请求可能改变已确认的会话，或在退出时丢失 | 进程间请求在确认接收前就能中止更新；已确认但仍在排队的请求同样优先于重启 |
| 准备完成的窗口仍可能自动保存或弹出外部文件重载提示 | 增加窗口准备状态；中止更新时恢复自动保存和延后的提示 |
| 仅等待父进程退出，可能将崩溃或交接超时误当成安装许可 | 增加排他决策文件；取消优先阻止后续批准，已批准后的取消等待退出后重新打开应用 |
| 安装程序在交接失败、检测失败或检测到更新版本时可能停留不退出 | 区分用户关闭与已完成操作的关闭，补齐非交互模式退出码及退出路径 |
| MSI 默认在事务之前移除旧产品 | 显式使用 `afterInstallInitialize`，让旧产品移除参与事务回滚 |
| 更新对话框依赖原窗口，偏好设置的模态循环还会阻挡写作 | 更新器拥有独立对话框；从偏好设置进入更新时结束偏好设置的模态循环 |
| 下载结束时未统一处理最后的缓冲区数据 | 最后一次读取仍经过相同的限额、写入及哈希处理 |
| 安装包校验后到执行前仍可被改写 | Windows 文件句柄只允许共享读取，覆盖校验、保存提示和启动交接阶段 |
| 更新安装包可能长期残留在临时目录 | 记录自己的下载目录；只清理已结束任务的已知文件，不递归删除未知内容 |
| 公钥变化未触发增量 CMake 配置，密钥初始化失败后不能重试 | 跟踪公钥输入并检查格式；初始化脚本重用匹配的本地密钥，拒绝静默更换信任根 |

## 回归约束

现有安装程序回归代码已加入“无批准不安装”“取消与批准冲突”和 MSI 移除顺序的断言。本轮未执行这些断言。

后续有合适条件时，仍需确认 Windows 的文件共享、Burn 启动与提升权限、拒绝 UAC、真实 MSI 回滚及多窗口恢复表现。代码审查不能代替这些运行结果。

## 发布约束

发布工作流使用 `MUFFIN_UPDATE_SIGNING_KEY` 签署更新清单，公钥固定在 `resources/update-public-key.txt`。签名密钥必须与内置公钥一致；缺少密钥或不匹配时拒绝发布可供应用内安装的更新。

本轮没有创建、更换或上传密钥，也没有提交、推送或发布版本。以后更换公钥应设计兼容迁移，不能直接替换现有用户信任的密钥。

## 2026-10-30：实际更新失败复查

用户报告“重启并更新”后编辑器不退出，随后显示安装程序未就绪。本机两次 Burn/MSI 日志表明，命令行确实包含隐藏的 `MuffinUpdate` 参数，但 BA 没有等待编辑器退出，直接进入普通安装流程。第一次 MSI 安装成功，第二次修复也成功；编辑器却因等不到交接标记而超时，报告了失败。

根因是自定义 BA 读取了 `Engine.GetVariableString("MuffinUpdate")`，没有解析 `IBootstrapperCommand` 中的命令行赋值。WiX 的 `Hidden` / `bal:Overridable` 声明不会替自定义 BA 完成这一步。此前的测试直接调用令牌解析器，未覆盖从真实 Burn 命令行进入 BA 的过程。

本次修复：

- BA 使用 WiX 的 `ParseCommandLine()`，只接收更新协议需要的 `MuffinUpdate`。缺失值、重复赋值、错误令牌或非被动安装模式均直接退出，不降级为普通安装。
- 保留“安装器确认就绪 → 编辑器明确批准并正常退出 → MSI 安装”的顺序，不强制终止编辑器。
- 交接失败后保留已经验证的下载，显示错误并继续提供“重启并更新”；重试前仍重新锁定并校验安装包。
- 每次交接使用 `update-<32 位 GUID>.ready` 及对应决策、取消文件，防止上一次超时后迟到的安装器干扰重试。新安装器仍接受旧版编辑器的 `update.ready` 格式；清理时同时识别两种格式，仅移除已知文件。
- 增加交接阶段日志；发布前运行实际安装包的命令行入口检查。

验证覆盖范围：

- 安装器测试通过 WiX 的真实命令行解析 API，再使用独立进程验证就绪、批准、正常退出、取消、无批准退出、迟到取消和重试；路径包含中文及空格。
- Qt 下载测试确认交接失败后按钮仍为“重启并更新”、保留错误信息和已下载字节，不发起重复下载。
- 对实际构建的 Burn 安装包，以完整交互模式传入不合法更新请求，确认其返回 1602，且日志中没有 Detect / Plan / Apply。使用完整交互模式是为了保证回归出现时也只显示安装页，不自动执行真实 MSI。
- Release 构建及完整 355 项 CTest 全部通过。已刷新 `build/dist`，并确认其中的可执行文件与 `build/Release` 的 SHA-256 一致。

以上检查不等于真实 MSI 升级、拒绝 UAC 和回滚的端到端验收。本次未执行实际升级，也没有修改已发布的 v0.7.8 资产；安装器入口修复需要随新的安装包分发，单独刷新编辑器的 `dist` 不能修复旧发布安装包。

## 2026-10-31：批准安装后旧编辑器仍不退出

v0.7.9 升级到 v0.7.10 的本机日志显示，安装器于 22:40:35 进入等待编辑器退出的阶段；编辑器约 100 毫秒后已经写入 `install` 决策。旧进程仍未退出，安装器于 22:42:35 等待满 120 秒后取消，未进入 Detect / Plan / Apply。此次停顿发生在下载完成后的交接阶段。

根因是更新对话框在 `Preparing`、`Installing` 状态拒绝关闭事件，而 `QApplication::quit()` 也需要关闭可见的顶层窗口。编辑器关闭文档窗口后，自己的更新对话框拒绝了应用退出。确认就绪后计时器已经停止，因此旧进程一直停留在“正在准备重启”，直到安装器一侧超时。

现在将已经持久化安装批准的阶段明确为 `Exiting`。只有写入并刷新安装决策成功后，更新对话框才允许正常关闭；等待确认期间仍拒绝关闭和 Escape。文件打开与文档重启保护在 `Exiting` 阶段继续生效，直到旧进程结束。取消交接则恢复原窗口与已验证的下载，不强制终止编辑器，也不直接跳过 Qt 的正常退出流程。

回归测试在独立的 Qt 进程中运行生产交接计时器和真实事件循环，覆盖：

- 安装器就绪前，编辑窗口与更新对话框均不能被误关闭。
- 就绪后写入 `install`，所有窗口关闭，Qt 正常退出，无需等待安装器的 120 秒超时。
- 安装器取消时写入 `cancel`，原文档窗口恢复编辑，已下载更新仍可重试。

这些回归覆盖编辑器的交接与退出，不执行真实 MSI 升级。已经发布的 v0.7.9、v0.7.10 编辑器都包含旧的关闭保护；新安装包中的修复不能改变正在运行的旧版本退出逻辑。

本轮验证：Release 构建、更新专项回归及完整 355 项 CTest 全部通过，1206 个 C/C++ 文件的格式检查通过。已重新生成 `build/dist`，其 `Muffin.exe` 与 `build/Release/Muffin.exe` 的 SHA-256 一致。本轮未修改既有版本附件，退出修复随 v0.7.11 发布；旧版本用户需要手动安装一次以获得修复。
